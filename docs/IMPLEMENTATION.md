# 真实实现、来源与验证记录

## 公开的是什么

本次发布是原项目代码的脱敏摘取，包含 3 个核心实现模块、1 个 Python 包标记文件和 4 个已有测试文件。不是重写聊天应用，也不是将完整线上目录直接公开。

| 公开文件 | 原模块职责 | 本次处理 |
|---|---|---|
| `src/trio_core/store.py` | 原服务端的 `Store` 类及房间权限表 | 提取类与常量，只保留标准库依赖；角色、房间、内部标识去身份化 |
| `src/trio_core/context.py` | 原任务执行器的上下文和提示词函数 | 提取 `context_records`、`context`、`incremental_context`、`build_prompt`；不包含模型执行或桥接 |
| `frontend/chat-state.js` | 原前端独立状态模块 | 使用没有重复定义的早期快照；角色与房间去身份化 |
| `tests/test_store.py` | 原存储回归测试 | 调整模块导入和通用标识 |
| `tests/test_paging.py` | 原服务端分页测试 | 调整模块导入和通用标识 |
| `tests/test_context.py` | 原任务执行器上下文测试 | 调整模块导入和通用标识 |

后端取自 2026-10-01 的本地开发快照；部分已有测试与前端状态模块来自较早的项目快照。这里没有核对最新线上代码。没有将旧文件伪装为最新发布，也没有复制原仓库提交历史。

## 代码能直接证明什么

### 事务与幂等写入

`Store.post()` 开启 SQLite 写事务，将消息、房间轮次与后继任务一起更新。同一身份、房间和请求键的重复提交返回既有消息编号。任务回传还验证房间、执行者、轮次与状态。

### 对话轮次与介入

自动回复累计六条后不再创建后继任务。用户的新消息提升该房间轮次并取消陈旧任务，迟到回传不能写入。失败恢复标记不确定任务供人工处理。

原代码还保留 `initiate=True`：受信任 Agent A 在没有活动任务时可以主动开始新话题，包括六条预算用完之后。因此这里的预算是自动回复链的停止机制，不是对任意高权限代理的绝对限制。已有测试明确记录了这一行为，公开时保留它而不是隐藏例外。

### 私密正文与上下文

`Store.read()` 和 `read_page()` 在返回给用户时隐藏未公开正文；`context_records()` 在构建公开回复上下文时排除未公开缓冲。指定角色执行公开后，缓冲区正文可以展示，并提升可见性版本。

`Store` 接收的是调用方传入的身份字符串，属于受信任的本地库。网络服务必须先认证，再映射身份；不能把这个 Python API 直接暴露成任意调用者可指定身份的公网接口。暂不公开不是加密，也不约束数据库所有者。

### 前端状态

`prepareSend()` 为相同待发送正文保留幂等键；`completeSend()` 检查对应操作，避免迟到成功回包清除另一个窗口或较新的草稿。`loadState()` 对损坏、旧版本或不可用存储回退默认值。

未读模块采用消息计数模型。它不能独立解决增量分页尚未补齐时的已读一致性，也不能证明页面滚动与认证恢复已经正确集成。

## 尚未验证或暂未公开

- `incremental_context()` 已作为原代码公开，但当前这组测试未直接覆盖其游标与截断分支。
- HTTP 登录、Cookie、跨站请求防护、生产部署与真实模型回调不在本次验证范围。
- 较新的完整页面代码曾发现空房间分页、未读提前清空、认证恢复和阅读位置问题，因此暂不作为可运行前端产品发布。
- 已有测试是回归证据，不是完整安全审计；不对并发负载、所有异常输入、所有跨渠道生成泄露作保证。

## 建议怎样展示这个项目

先展示具体机制，再展示对应测试。例如：从用户介入后的迟到回传拒绝，看 `Store.post()` 的轮次检查；从重复提交返回相同消息编号，看事务内的请求键去重；从切换窗口后保留草稿，看前端状态测试。这样可以让读者看到设计如何落到实际代码，而不是仅有框架图。
