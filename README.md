# Trio：人与双 AI 的多房间对话设计

Trio 是一个围绕「一名用户、两个 AI、多个对话空间」展开的个人项目。本仓库提炼其通用产品设定：谁能参与对话、谁能读取内容、AI 可以自主交流多久，以及人类如何介入。

这是经过脱敏的设计与代码案例，包含从原项目提取的核心源码、已有回归测试、设计规则和虚构示例。不包含真实聊天、生产配置或在线 AI 接入。本仓库可本地运行核心测试，不是完整聊天产品的部署包。

## 想解决的问题

当两个 AI 与用户共同交流时，单一聊天流难以同时承载群聊、私聊和 AI 之间的讨论。共享记忆可以维持连续性，却也需要明确的消息投递边界；自动对话则需要由用户控制的停止与继续机制。

Trio 将这些问题拆成三个可以解释和检查的规则：

- **空间与权限**：对话发生在哪个房间，决定参与者和可读取范围。
- **连续性与投递**：记忆可以跨渠道连续，消息只投递到指定房间。
- **自主性与控制权**：AI 可以有限交流，用户可以暂停、介入并明确继续。

## 房间结构

最初的三窗口包含三人群聊、用户与其中一个 AI 的私聊，以及两个 AI 的交流。后续设计补齐另一条人机私聊，形成四房间结构。下表使用通用角色名。

| 空间 | 可发言者 | 应用内可读取者 | 用途 |
|---|---|---|---|
| 三人群聊 | 用户、Agent A、Agent B | 三者 | 共同讨论 |
| 用户与 A | 用户、Agent A | 用户、Agent A | 人机私聊 |
| 用户与 B | 用户、Agent B | 用户、Agent B | 人机私聊 |
| A 与 B | Agent A、Agent B | 两个 AI；用户可旁观已公开部分 | 双 AI 讨论 |

详细规则见 [设计说明](docs/DESIGN.md)，交互示例见 [虚构演示](docs/DEMO.md)。

## 关键机制

1. 双 AI 自动回复链最多三轮，即六条 AI 消息；达到预算后暂停。用户可明确继续；原代码还保留受信任代理主动开启新话题的独立入口，详见实现说明。
2. 用户在某房间的新输入使该房间的陈旧任务失效，其他房间不受影响。
3. 回复绑定服务端任务中的房间和身份，防止跨房间回写。
4. 发送使用幂等键；失败或结果不确定时，由用户决定重试。
5. 双 AI 房间支持「暂不公开」缓冲区；其中的回复继承可见性，指定角色可将其公开。
6. 每个房间保留独立草稿、阅读位置和未读状态。

## 设计边界

房间权限约束应用接口和上下文选择，不等同于对设备所有者保密。共享模型上下文时，渠道之间的生成内容边界也依赖模型遵守指令，不能将其描述为绝对隔离。核心代码与测试见下文；测试只覆盖提取模块，不代表完整网页或当前线上版本已通过验收。

公开范围与脱敏处理见 [发布说明](docs/PUBLICATION.md)。

## 本地运行

使用 Python 3.10+ 与 Node.js 18+，无需安装第三方库。以下版本范围来自语法和测试运行器要求；本次实测版本记录在实现说明中。

在仓库根目录执行：

```sh
# macOS / Linux
PYTHONPATH=src python -m unittest discover -s tests -p 'test_*.py' -v
node --test tests/test_chat_state.cjs
```

```powershell
# Windows PowerShell
$env:PYTHONPATH = Join-Path (Get-Location) 'src'
python -m unittest discover -s tests -p 'test_*.py' -v
node --test tests/test_chat_state.cjs
```

## 阅读顺序

1. 从 `tests/test_store.py` 看权限、幂等写入和轮次预算的行为。
2. 对照 `Store.post()` 看消息和任务怎样在同一个事务内保存。
3. 从 `context_records()` 看未公开正文如何从公开上下文中排除。
4. 从 `prepareSend()` 与 `completeSend()` 看失败重试和迟到回包如何处理。

完整网页、HTTP 登录层、模型命令行适配器和私有渠道桥接暂未发布。原前端分页集成曾发现待修问题；本次公开状态模块不代表那些问题已经修复。
